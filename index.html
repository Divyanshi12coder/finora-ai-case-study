Problem → solution

Money data is plentiful and hard to use

Hover over a card (or tap it on a phone) to flip from the problem to the part of Finora that addresses it. Every answer corresponds to real code.

Problem 01

Manual categorisation

Bank narrations look like this, and someone has to turn them into "Food":

UPI/SWGGY/428391/Food orderHover to see the fix
Solution

Explainable ML categoriser

Word + character TF-IDF → Logistic Regression suggests a category while the user types, with confidence and the tokens behind it. It applies automatically only at ≥ 45% confidence.

Problem 02

Hidden spending patterns

Monthly totals don't show which category or merchant caused a change, or whether a partial month is being compared with a full one.

Hover to see the fix
Solution

Analytics + insight engine

Equal-length period comparison and 8 deterministic detectors. A change is reported only when it is both ≥ 18% and ≥ ₹500.

Problem 03

Unexpected transactions

Fixed rules like "flag anything over ₹5,000" don't fit anyone's real spending.

Hover to see the fix
Solution

Per-user anomaly detection

Median/MAD z-score per category plus an Isolation Forest, each flag with a reason a person can read.

Problem 04

No forward view

People want to know what next month is likely to look like, and how sure the estimate is.

Hover to see the fix
Solution

Forecasts that state their uncertainty

The model depends on how much history exists, with an 80% interval. There is no forecast below 3 months, and the app says why.

Problem 05

Receipts stuck on paper

Merchant, date, the CGST/SGST split and the total all have to be retyped.

Hover to see the fix
Solution

OCR the user reviews

OpenCV → Tesseract → rule-based parser with per-field confidence. Nothing reaches the ledger until the user confirms.

Problem 06

AI that invents figures

Ask a language model about your money and it will give you a plausible number, right or wrong.

Hover to see the fix
Solution

Facts first, wording second

Typed tools query PostgreSQL and Python does the arithmetic. The LLM only rephrases. With no API key, the answers contain the same numbers.

The organising rule

The backend computes the facts. The AI explains them.

Remove the AI provider and the product still works. Every figure stays the same and only the prose gets plainer, and the UI labels which mode produced each answer.

Deterministic code owns

  • Every query, scoped by user_id
  • All arithmetic
  • Which tools run
  • Thresholds and refusals

The LLM may only

  • Rephrase verified JSON facts
  • Carry caveats through
  • Say "not available"
  • Never add a number
System architecture

Follow a request down the stack

Scroll through the steps and the layer each one describes lights up in the diagram. ML, OCR and the LLM are optional: each reports whether it's available, and the API starts without any of them.

STEP 1 · BROWSER

A React SPA with no secrets

16 pages built on one api/client.ts. It's the only place that calls fetch. It attaches the JWT, applies a 30-second timeout, parses FastAPI's field errors and routes any 401 back to login.

STEP 2 · EDGE

nginx serves the app and proxies the API

The browser always calls a relative /api, so there's one origin and no CORS preflight. nginx also sets the CSP and security headers.

STEP 3 · API

Thin routers and one auth gate

Pydantic validates each request, and get_current_user turns the JWT into a user. Middleware adds X-Request-ID and timing headers. Routers hold no business rules.

STEP 4 · LOGIC

Services, and repositories that require an owner

14 services hold the logic. Every repository helper takes a user_id, so there's no query that can return another user's rows, and cross-user access returns 404.

STEP 5 · INTELLIGENCE

ML, OCR, insights and AI

These are pure computation modules that never touch the database directly. The LLM, shown dashed, is called only if AI_API_KEY is set, and it receives facts only.

STEP 6 · DATA

PostgreSQL is the single source of truth

13 tables and Numeric(14,2) for money. Derived values are computed on read, and Alembic migrations are checked in CI by applying them up, down and up again.

ML pipeline

From a raw narration to a category you can trust

Keep scrolling and the pipeline moves sideways. Training and serving import the same preprocessing module, so what the model learned is exactly what it's asked to predict.

01 · INPUT

Raw text

Merchant, description, payment method and transaction type, exactly as the bank wrote them.

UPI/SWIGGY/428391/Food order
02 · NORMALISE

Preprocess

NFKD accent stripping and lowercasing. Card numbers, amounts, dates and 6+ digit reference numbers are masked, and narration stop tokens are dropped.

→ upi swiggy food order
03 · COMPOSE

Build the document

The merchant is repeated twice to up-weight the strongest signal. Payment method and type become prefixed tokens.

swiggy swiggy … pay_upi type_expense
04 · FEATURES

TF-IDF union

Word 1–2 grams for merchants and phrases, plus char_wb 3–5 grams so misspellings like SWGGY and AMAZONIN still match.

word ×1.0 ⊕ char ×0.6
05 · MODEL

Logistic Regression

Multinomial, C=4, balanced classes, 12 categories. It trains in seconds on CPU, so the Docker image trains it during the build.

predict_proba → top-k
06 · EXPLAIN

Why this category?

For a linear model, each token's contribution is tfidf × coefficient, so the UI can show which words drove the prediction.

[swiggy, food, order]
07 · POLICY

Confidence gate

At ≥ 0.45 the category is applied, and at ≥ 0.70 it's marked high confidence. Anything lower is only a suggestion, because a wrong category corrupts every chart after it.

apply ≥ 0.45 · high ≥ 0.70
08 · LEARN

Correction loop

Overrides set was_corrected in ml_predictions. They're exported (text only), used in retraining, and loaded without a restart.

export → train → reload_model()

1

Deterministic routing

Ordered regex rules pick at most 4 of 13 tools. The LLM never chooses what data to fetch, so a prompt injection can't request arbitrary data.

2

Typed tools query PostgreSQL

Each tool returns structured data plus a readable summary, always scoped to the signed-in user.

3

Python does the arithmetic

"How much can I save if I cut shopping by 20%?" The percentage is parsed from the question and get_savings_simulation computes the answer.

4

Phrase, or fall back

If a key is set, the LLM gets a verified JSON block of facts and is told never to add a number. With no key or on any error, the tool summaries are joined into the answer instead, with the same figures.

5

Show the source

Each answer comes back with its tool trace, the facts and generation_mode. A test checks that a broken provider still returns correct numbers.

Not built yet: a check after generation that every number in the LLM's reply appears in the facts. For now, the architecture and the prompt enforce this rule; the output itself isn't validated.

    Security

    Protections built into the structure, gaps listed

    Most protections come from how the code is organised, so no individual route has to remember them. The known gaps are listed below the cards.

    Passwords

    bcrypt with cost 12, plus SHA-256 pre-hashing for passwords longer than 72 bytes. A malformed hash fails closed instead of erroring.

    JWT

    Signature, expiry and type == "access" are checked on every request. Tests confirm forged tokens are rejected.

    No account enumeration

    Login takes the same time for unknown emails, and forgot-password gives the same response either way.

    Data isolation

    Every query needs a user_id, and other users' data returns 404. Ten tests cover this.

    Input validation

    Pydantic on every endpoint, a whitelisted ORDER BY and parameterised queries throughout.

    Uploads

    An 8 MB limit, a MIME allow-list, magic-byte checks and server-generated filenames.

    CORS & headers

    An explicit list of allowed origins (never *). nginx adds a CSP, nosniff and X-Frame-Options: DENY.

    Secrets

    Secrets live only in environment variables. Docker Compose refuses to start without JWT_SECRET, and the frontend holds none.

    Logs

    Passwords, tokens and keys are redacted from logs, SQL errors never reach the client, and the container runs as a non-root user.

    Known gaps, not yet addressed

    • No rate limiting on /auth/login or /ai/chat.
    • No token revocation: logging out doesn't invalidate a token, which stays valid until it expires (12 hours by default).
    • The JWT is kept in localStorage. The CSP reduces XSS risk, but an httpOnly cookie would be safer.
    • Receipt images are stored unencrypted on disk.

    Engineering challenges

    What was hard, and how it was solved

    Drag, swipe or use the arrows. Each challenge is traced to code, a test or a commit, and one is still open.

    01ml/preprocessing.py

    Train/serve skew

    Problem
    The model is trained from the repository root but served from backend/, so the two could normalise text differently without anyone noticing.
    Fix
    One shared ml package, PYTHONPATH=/srv in Docker, and a PIPELINE_VERSION check when the model loads.
    02ml/build_dataset.py

    A model that scored 100%

    Problem
    Every merchant mapped to exactly one category, so the model was just a lookup table.
    Fix
    A harder dataset with ambiguous and garbled merchants, a test that fails at 1.0, and a CI check that the dataset regenerates byte-for-byte.
    03ocr/parser.py

    Noisy OCR output

    Problem
    Skewed photos, plus a regex that read ₹1,923.60 as ₹3.60.
    Fix
    Image preprocessing, per-field confidence, a review step before saving, and a regression test.
    04ml/anomaly.py

    Statistics on real spending

    Problem
    Identical subscription payments make MAD zero, and a single large purchase distorts the mean.
    Fix
    MAD with fallbacks, per-category baselines, and Isolation Forest flags that only count when z ≥ 2.
    05ai/assistant.py

    Unreliable LLM output

    Problem
    LLMs invent figures, and the provider can time out.
    Fix
    Retrieval first, arithmetic in Python, a constrained prompt, and a fallback that gives the same figures.
    06ci.yml

    Reversible migrations

    Problem
    Migrations that only go forward, and SQLite in development ignoring foreign keys.
    Fix
    Migrations run up → down → up on real Postgres in CI, SQLite foreign-key enforcement is switched on, and the container waits for the DB before migrating.
    07commit f3d7aa4

    Build broke on deploy

    Problem
    tsc -b failed because the Vite config uses node:path without Node's type definitions installed.
    Fix
    Added @types/node. Lesson: run the same build locally that the host runs.
    08commit b6a88f8

    One nginx config, two environments

    Problem
    Pointing proxy_pass at Render means local Compose now proxies to production.
    Open
    Planned fix: generate the upstream from an environment variable with envsubst and set proxy_ssl_server_name on.

    Key decisions and their trade-offs

    The LLM only rephrases verified facts; tool routing is rule-based
    WhyCorrectness, auditability and resistance to prompt injection, and it works offline.
    Trade-offLess flexible than LLM tool-calling; unusual phrasings may be routed badly.
    TF-IDF + Logistic Regression rather than a deep model
    WhyTrains in seconds on CPU, gives calibrated probabilities, has explainable coefficients, and trains during the Docker build.
    Trade-offA lower ceiling on understanding meaning; relies on feature engineering.
    Apply categories automatically only above 0.45 confidence
    WhyA wrong category that nobody notices costs more than asking the user.
    Trade-offMore prompts for ambiguous merchants.
    Rule-based receipt parser
    WhyAuditable, needs no GPU or third party, and reports confidence per field.
    Trade-offBrittle on receipt layouts it hasn't seen.
    Compute derived values on read
    WhyThey can never drift from the ledger.
    Trade-offMore work per request, and there's no caching yet.
    Stateless JWT kept in localStorage
    WhySimple, scales horizontally, and needs no session store.
    Trade-offNo revocation, and exposure to XSS (reduced by the CSP).

    What I learned

    Lessons from building it

    The biggest shift was treating the model as one component among many. Most of the engineering went into the code around it.

    Full-stack architecture

    With one layer per concern, data isolation is enforced in one place instead of in every route.

    Production ML

    Shared preprocessing, versioned artefacts and a confidence policy mattered more than which classifier I picked.

    API design

    Action sub-resources, one error shape and explicit "insufficient data" responses made the frontend simpler.

    Database design

    Decimal for money, derived values computed on read, and indexes designed around the real queries.

    OCR

    Preprocessing drives most of the accuracy. For the remaining errors, show the confidence and ask the user.

    Deployment

    A setup that works in Compose still needs changes for a managed host. Config should be templated, not edited in place.

    Security

    Protections built into the structure beat checks added route by route, and the gaps should be written down.

    AI system design

    An assistant that stays correct with the model switched off is one people can trust.
